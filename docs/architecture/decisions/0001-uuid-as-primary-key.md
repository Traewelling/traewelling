# ADR-0001: UUIDs as primary keys

- **Status**: accepted
- **Date**: 2026-08-08 (recorded retroactively, the decision predates this ADR)
- **Deciders**: Träwelling maintainers
- **Related**: `API_CHANGELOG.md`

> This ADR was written after the migration had already started, in order to preserve the
> reasoning before it is lost. It reconstructs the decision, it did not precede it.

## Context and Problem Statement

Historically every entity used an auto-incrementing integer primary key, and that integer
was also the identifier exposed by the public API and by web URLs.

A sequential public identifier leaks information that nobody agreed to publish. Anyone can
walk `/status/1` to `/status/n` and enumerate the entire corpus, which turns per-status
visibility rules into the only line of defence against systematic scraping. The highest
observed id tells outsiders how many statuses, users or trips exist and how fast the
numbers grow. For a service whose core data is the movement profiles of real people, that
is the wrong default.

At the same time, the public API is consumed by third parties we cannot deploy for. Any
change to how entities are identified is a breaking change with a long tail.

## Decision Drivers

- **Privacy**: identifiers must not be enumerable and must not disclose volume or ordering.
- **Operational flexibility**: entities must be creatable, mergeable and importable
  without renumbering.
- **API stability**: the transition must be possible without a hard break for third party
  clients.
- **Deployability**: `develop` is deployed continuously, so every intermediate state must
  be correct on its own. Tables such as `statuses` and `train_stopovers` are large enough
  that a blocking `ALTER TABLE` is not acceptable.
- **Three production database drivers**: MySQL, MariaDB and SQLite. Every migration step
  must work on all of them, including on instances too small to have an operator watching
  the upgrade.

## Considered Options

1. Keep the integer primary key, expose a separate public UUID or slug.
2. Migrate the primary key itself to a random UUID (version 4).
3. Migrate the primary key itself to a time ordered UUID (version 7).
4. Use ULIDs.

## Decision Outcome

Chosen option: **3, a UUID primary key, generated by the application, time ordered where
possible**, stored as `CHAR(36)` and exposed as the identifier in the public API.

Concretely:

- New tables get `$table->uuid('id')->primary()` from the start.
- New models use Laravel's `HasUuids` trait, which in the framework version currently in
  use generates **UUID version 7**, so new rows are roughly insert ordered.
- Existing tables are migrated model by model, not in one big bang, see the migration
  strategy below.
- Foreign keys follow the primary key to UUID as each model is migrated.
- The API exposes the UUID. Legacy integer ids are deprecated per resource through
  `API_CHANGELOG.md` with a transition window of at least six months.

Option 1 was rejected because it keeps every drawback of the integer key inside the
database, keeps two identities alive permanently, and leaves the door open for the
internal integer to leak through some endpoint or error message. If the public identifier
is a UUID anyway, the second identifier is pure overhead.

Option 2 was rejected as the target state: fully random keys are a poor clustered index in
InnoDB, where the primary key determines physical row order. Random inserts scatter across
the B-tree, increase page splits and fragmentation, and every secondary index carries a
copy of the primary key. On the largest tables this is a measurable cost.

The rejection applies to the target state only. During the transition the `uuid` columns
hold a mix of versions:

- **Backfilled rows** get whatever the driver can produce cheaply for millions of rows.
  MySQL and MariaDB use the native `UUID()`, which returns **version 1**. The SQLite path
  uses `Str::uuid()`, which returns **version 4**.
- **New rows** on a model that still has an integer primary key get **version 4**, from a
  `creating` hook that calls `Str::uuid()`, because `HasUuids` cannot be used while the
  primary key is still the integer.
- **New rows** on a model that has already flipped get **version 7**, from `HasUuids`.

This is accepted rather than intended. Those values are unique identifiers, never a sort
key, and rewriting them would cost another full table pass on exactly the tables the
staged migration exists to avoid rewriting. The practical consequence is that the
insert ordering benefit of version 7 only materialises for rows written after a model has
flipped, not retroactively.

Option 4 was rejected for ecosystem reasons rather than technical ones. ULIDs give the
same ordering benefit as version 7 UUIDs, but they are less universally understood by API
consumers and less widely supported by tooling.

### Consequences

**Good**

- Identifiers are no longer enumerable, and no longer disclose record counts or growth.
- References stay valid across merges and across possible future instances.

**Bad**

- Storage and index size grow. `CHAR(36)` costs significantly more than an 8 byte integer,
  multiplied across every secondary index and every foreign key column.
- A breaking change for every third party API consumer, per resource, with a long
  deprecation window to manage.
- The migration is long running and touches nearly every table, so the codebase spends an
  extended period in a mixed state.

## Migration Strategy

Per model, four phases, each individually deployable:

1. **Add**: add a nullable `uuid` column, backfill existing rows in batches, then add the
   unique index. On MySQL / MariaDB the column is added with
   `ALGORITHM=INPLACE, LOCK=NONE` so large tables stay writable. On SQLite the portable
   `Schema::table()` path is used instead, guarded by a driver check.
2. **Adopt**: application code and the public API start using the UUID. Endpoints accept
   both the legacy integer and the UUID. The new `uuid` field appears in API resources and
   the integer `id` is announced as deprecated in `API_CHANGELOG.md` with a "safe until"
   date at least six months out.
3. **Repoint**: foreign keys of referencing tables are migrated to the UUID.
4. **Drop**: after the announced date has passed and all references are gone, the integer
   column is removed and the UUID becomes the primary key. On SQLite this requires
   rebuilding the table, since the driver cannot alter a primary key in place.
